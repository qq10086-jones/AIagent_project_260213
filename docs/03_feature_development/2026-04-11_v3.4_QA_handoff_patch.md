## 二、设计方案

### 2.1 QA Executable Verification（学习 MetaGPT）

**核心思路**: 不依赖 PM 生成 verify_command。由 smoke_test 步骤**自动从 handoff 合约生成可执行测试**。

**实现**: 在 `workflow_step_builder.js` 的 smoke_test payload 构建中:

1. 读取 `handoff/architect_to_impl.json` 的 interfaces 数组
2. 对每个端点生成 curl probe 命令（GET → 期望 200，POST → 期望 201/400）
3. 注入到 smoke_test 命令的 `--api-endpoints` 参数
4. `run_smoke_test.mjs` 扩展：逐个 probe 声明的端点，写入 smoke_result.json

**效果**: smoke_result.json 从只检查 `/` 和 `/api/customers` 变为检查全部 13+ 端点。

### 2.2 Handoff Coverage Guard（学习 MetaGPT SOP）

**核心思路**: handoff 不仅检查 schema，还检查**内容覆盖度**。

**实现**: 在 `coding_team_handoff_validators.js` 的 `validateCodingTeamHandoff` 中:

1. impl_be 的 be_to_fe.json:
   - `api_contracts` 数量 >= architect_to_impl.json 的 interfaces 数量的 50%
   - 如果 arch 声明了 N 个端点，be_to_fe 至少文档化 N/2 个
2. impl_fe 的 impl_to_qa.json:
   - `run_instructions` 不能是通用模板，必须包含实际命令
   - 必须引用 be_changes_path 和 fe_changes_path

### 2.3 Smoke 全端点覆盖（学习 Cursor BugBot）

**核心思路**: smoke 不只检查首页，覆盖全部声明端点。

**实现**: 修改 `scripts/run_smoke_test.mjs`:

1. 接受 `--api-endpoints` JSON 参数
2. 对每个 GET 端点发 curl，检查 status 200
3. 对每个 POST 端点发 minimal body，检查 status 201 或 400（不是 404/500）
4. 结果写入 smoke_result.json 的 `endpoint_probes` 数组

### 2.4 Handoff Scaffold Goal-Aware（修复 3/10 根因）

**核心思路**: be_to_fe.json 和 impl_to_qa.json 的 scaffold 模板也要 goal-aware。

**实现**: 在 `artifact_scaffold.js` 的 be_to_fe.json 和 impl_to_qa.json 模板中:

1. 使用 `extractGoalModules()` 提取全部模块
2. be_to_fe.json 的 api_contracts 覆盖每个模块的主要端点
3. impl_to_qa.json 的 run_instructions 引用实际文件路径
