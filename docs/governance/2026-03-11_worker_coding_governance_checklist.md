# Worker-Coding Governance Checklist

- Date: 2026-03-11
- Scope: next-stage coding capability uplift after M9 closeout
- Authority: Governance v3 + Design v4.x + current M9 closeout state

---

## 1. Decision

Current worker-coding capability uplift is classified as:

`MAINLINE TYPE A`

Reason:

- it directly strengthens the North Star node `OpenClaw Orchestration -> Coding Team Workflow -> Artifacts`
- the current project skeleton is already validated enough to shift from infrastructure closeout into productized coding execution
- the work is not a side optimization; it determines whether the coding workflow is usable by real internal users

This is not a new milestone yet.

It is a governed mainline capability program under the current post-M9 stage.

---

## 2. Strategic Position

The project must not narrow itself into a single demo use case.

`build a webpage` may be used only as:

- one standard regression sample
- one beta entry scenario
- one onboarding example for internal testers

It must not be treated as:

- the sole product direction
- the only acceptance scenario
- justification for frontend-only optimization

The governed target is broader:

`make worker-coding reliably useful across a controlled set of coding task classes`

Initial controlled task classes:

- create a small webpage or landing page
- modify an existing frontend page or component
- implement a small backend endpoint or handler
- repair a scoped defect with explicit verification
- produce required artifact bundles for workflow handoff

`none`

## 4. Mandatory Guardrails

Every worker-coding subtask must answer all items below before execution:

1. Which North Star node does this directly strengthen?
2. Which task class does this improve?
3. What explicit contract changes, if any, are introduced?
4. What validation evidence will prove the improvement?
5. What is explicitly out of scope?

Reject the task if the answer is primarily:

- "better future flexibility"
- "more powerful agent behavior"
- "cool demo potential"
- "more general autonomy"

---

## 5. Controlled Task-Class Matrix

Worker-coding improvements must be reviewed against these task classes:

| Task Class | Beta Importance | Why It Matters |
|-----------|-----------------|----------------|
| FE Create | High | validates greenfield page delivery |
| FE Modify | High | validates real repo editing usefulness |
| BE Create | High | validates non-frontend narrowness |
| Bug Fix | High | validates precision + verification loop |
| Artifact Repair | Medium | validates workflow handoff robustness |

No single class may dominate roadmap decisions without explicit review.

---

## 6. Quality Gates

Before a worker-coding workstream is marked done:

- contract note exists
- targeted tests exist
- release-gate or cohort validation evidence exists
- failure mode is observable
- artifact output remains structured
- non-scope was respected

---

## 7. Anti-Narrowing Rules

The following are governance violations for this program:

- defining success only as "can generate a webpage"
- optimizing prompts only for one frontend stack
- accepting improvements that regress backend or bug-fix task classes
- adding task-class-specific hacks without documenting cohort boundaries
- expanding provider/runtime complexity before current cohorts are stable

---

## 8. Current Recommendation

Proceed with worker-coding capability uplift as the next governed mainline program.

Execution should focus on:

1. task-class coverage
2. first-use success rate
3. verification reliability
4. artifact quality
5. controlled beta evidence
